## 2026-09-03 CI is load-bearing for macOS safety but unmonitored

- Status: accepted
- Topics: testing, safety, CI
- Refs: `.github/workflows/test.yml`, 2026-02-18 Docker-only test runs
- Decision: Enable failure-only Actions notifications (account setting, not in this repo) and keep
  pushing straight to master. No PR gating for now.
- Rationale: Notifications close the "nobody reads it" half at zero cost. PR gating would make the
  native macOS leg preventive rather than after-the-fact, and it is the only check that could ever
  be preventive since it cannot run in pre-push by design, but it charges a branch and a PR for
  every one-line dotfile edit. Revisit if a red master goes unnoticed despite the notifications.
- Alternatives: branch protection requiring only `test-macos` (the other three checks already run
  in pre-push, so requiring all four would just re-run what passed locally); a workflow job that
  files a `ci-failure` issue on failure, which persists where an email scrolls past.
- Problem: Docker-only local testing pushes native macOS coverage onto CI, so CI is the only thing
  standing behind bash 3.2 + BSD userland. I do not watch CI runs, and pushes go straight to
  master, so a red macOS leg can land and sit unnoticed. An unwatched boundary still contains
  damage, but it stops being a signal.
- Options: PR-gated workflow with required checks instead of direct master pushes; notifications
  on failure only; pre-push already runs Docker tests, so the missing piece is specifically the
  native leg, which cannot run locally by design.
- Consequences of leaving it: the macOS regression that CI catches is one nobody reads.
- Note: Deliberately out of scope of the conversation that surfaced it. The native integration
  gap that surfaced alongside it is now closed: the cause was `cp -r` (see the 2026-08-26 entry's
  correction), and `test-macos` runs the full suite as a blocking job, so `symlink-manager.sh` has
  native coverage on the platform whose `$HOME` it writes to. That makes CI strictly more
  load-bearing than when this entry was written, not less.

## 2026-08-28 pr-feedback emits human feedback only, no mode flags

- Status: accepted
- Topics: agent scripts, pr-feedback
- Refs: `src/dotfiles/.claude/scripts/pr-feedback.mjs`
- Decision: Only arg is an optional PR number. Bot-authored (`author.__typename == "Bot"`)
  top-level comments and reviews are always dropped (counted in `botFeedbackOmitted`); bot inline
  threads are kept. Also for payload size: no `diffHunk` (path + line locate a comment), and
  inline comments are fetched once via `reviewThreads`, never per review.
- Rationale: `--unresolved` silently hid outdated-but-unresolved threads, the key category when
  checking whether requested changes landed. Type-based bot filtering needs no login list and
  fixed the payload-size problem the flag existed for.
- Consequences: Bot output comes from gh directly when needed. Resist a bot allowlist until a
  bot with real top-level feedback actually appears.

## 2026-08-28 Canonical shared agent configuration

- Refs: `Canonical agent skills in .agents/skills`, `src/dotfiles/.agents/`,
  `src/dotfiles/.claude/`, `src/dotfiles/.codex/`, `config`
- Decision: Keep cross-agent instructions and skills canonical under `~/.agents`; retain thin
  client-specific imports or symlinks where a client requires its own discovery path.
- Rationale: One source prevents guidance drift while adapters preserve each client's supported
  discovery behavior.
- Consequences: Put new shared content under `.agents`; add a client adapter only when that client

  content needs tool-specific behavior, break only that adapter and keep the common core shared.

  files for clients before their behavior diverges.

## 2026-08-28 Canonical agent skills in .agents/skills

- Status: superseded
- Topics: agent config, symlinks
- Refs: `Canonical shared agent configuration`
- Decision: Cross-tool skills (review, humans-dont-like-to-read) live canonically in `.agents/skills/` (the universal Agent Skills layout Codex and others scan natively via `~/.agents/skills`). Claude Code doesn't read that path, so `.claude/skills/<name>` entries are tracked relative symlinks into `.agents/skills/`. No wrapper/import files.
- Rationale: Both tools consume identical SKILL.md; a symlink is zero-maintenance vs wrappers that instruct "read the core file" (extra hop, duplicated frontmatter, silent rot). Same tracked-relative-symlink pattern as `.zsh/plugins`.
- Consequences: If a skill ever needs tool-specific behavior, break only that symlink: make `.claude/skills/<name>/SKILL.md` a real thin wrapper pointing at a shared `core.md` kept in `.agents/skills/<name>/`. Until then, edit skills under `.agents/skills/` in the repo checkout for git awareness.
- Alternatives: codex-canonical with claude symlinks (ties content to one vendor's dir); wrapper files both sides (maintenance for drift that hasn't happened).

## 2026-08-26 Stay bespoke — no chezmoi/stow migration

- Status: accepted
- Topics: architecture, dotfile management
- Refs: `src/symlink-manager.sh`, `README.md`
- Decision: Keep the custom symlink manager and vendored-submodule plugin handling; no migration to chezmoi, stow, or any dotfile manager.
- Rationale: chezmoi's copy model breaks edit-from-either-side + nvim git integration (symlink transparency is the design's best property); submodules beat chezmoi externals for pinning + audit (`git log old..new`); the test breakdown showed ~65% of the suite guards the personal scripts, which survive under any manager — migration would delete little.
- Alternatives: chezmoi (better templating/adopt, wrong model); stow (same model, does less); bare git repo (rejected in 2020).

## 2026-08-26 Shell dialect layering

- Status: accepted
- Topics: scripting, portability
- Refs: `src/dotfiles/.local/bin/`, `src/dotfiles/.zsh/functions.zsh`, `CLAUDE.md`
- Decision: Three layers — POSIX sh where trivial (`sysinfo`), bash 3.2 for standalone scripts, zsh only for interactive shell-integration functions. No brew bash, no zsh migration.
- Rationale: `/bin/bash` 3.2 is frozen (stable target, exists on every macOS and Linux box); zsh scripts wouldn't run in bare containers; the 3.2 floor is now CI-enforced (macOS unit-test leg), so the constraint costs ~nothing.
- Alternatives: migrate scripts to zsh; require brew bash 5 + env shebangs (splits bootstrap vs daily scripts into two regimes).

## 2026-08-26 Conditional test selection via @covers headers

- Status: accepted
- Topics: testing, git hooks, CI
- Refs: `.githooks/pre-push`, `tests/`, `src/doctor.sh`
- Decision: pre-push runs only tests whose `# @covers <path|glob>` header matches a changed file; unmatched changes fail open to the full suite; doctor validates the headers; CI stays full-suite as backstop.
- Rationale: Declared map beats grep-derived (script names like `e` are ungreppable); staleness is contained by doctor + fail-open, not memory.
- Alternatives: grep-derived map; central map file; no conditioning.
- Accepted gap: a guarded optional dependency between dotfiles is unmapped until a test exercises it — a miss costs a CI failure email, not a blocked push.
- Scope note: the macOS CI job runs unit tests only — integration tests are container-shaped (86 native failures at time of writing). First native run caught a real bash 3.2 bug in envsync (`set -u` + empty arrays).
- Correction 2026-09-03: "container-shaped" was a misdiagnosis. All 86 failures had one cause,
  `cp -r` in the four integration `setup()` functions: BSD `cp -r` dereferences symlinks and fails
  on the dangling ones under `vendor/tmux/tmux-resurrect` (its nested `lib/tmux-test` submodule is
  never initialized), while GNU treats `-r` as `-R` and preserves them, hiding it in Docker.
  Fixed by using `cp -R`. The integration tests were never container-shaped; nothing had ever run
  them natively to find out.
